# 支付服务超时

## 现象

- 用户下单后卡在「支付中」，10 秒后提示失败
- 监控上 `pay-service` 的 P99 从 300ms 涨到 3s 以上
- 网关侧出现大量 504

## 影响范围

支付链路是成交的最后一步，超时直接造成资损（用户重新下单可能重复扣款）。

## 排查步骤

1. 看 `pay-service` 的 P99、QPS、错误率三个指标，确认是「变慢」还是「报错」
2. 看下游依赖：`pay-service` 调用的第三方支付渠道是否超时
3. 看线程池 / 连接池使用率，是否被打满
4. 搜日志关键字：`timeout`、`Read timed out`、`ConnectException`
5. 查最近 2 小时有没有发版

## 常见根因

| 根因 | 典型证据 |
|---|---|
| 第三方支付渠道抖动 | 日志里全是 `Read timed out`，本地 CPU 正常 |
| 数据库连接池打满 | 日志有 `HikariPool` / `connection is not available` |
| 发版引入慢查询 | 发版时间点之后 P99 阶梯上涨 |
| 下游限流 | 大量 429 / `rate limit exceeded` |

## 处置动作

- 第三方渠道问题：切备用渠道，或降级为「稍后重试」提示
- 连接池打满：临时调大 `maxPoolSize`，同时排查慢 SQL
- 发版导致：立即回滚
- 下游限流：本地加排队 + 退避重试

## 升级条件

15 分钟内无法定位，或资损面扩大，直接拉起支付值班群 + 通知业务方。
