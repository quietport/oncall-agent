# 数据库连接池耗尽

## 现象

- 接口大面积超时，但服务器 CPU、内存都不高
- 日志大量出现 `HikariPool-1 - Connection is not available, request timed out after 30000ms`
- 数据库侧 `Threads_running` 飙高

## 影响范围

连接池是共享资源，一个慢 SQL 会拖垮整个服务的所有接口。

## 排查步骤

1. 确认日志里是否有 `Connection is not available`
2. 查数据库的慢查询日志，找执行时间 > 1s 的 SQL
3. 看是否有全表扫描（`rows_examined` 远大于 `rows_sent`）
4. 确认连接池配置：`maximumPoolSize`、`connectionTimeout`
5. 检查是否有长事务未提交

## 常见根因

| 根因 | 典型证据 |
|---|---|
| 慢 SQL 占用连接 | 慢查询日志里有同一条 SQL 反复出现 |
| 连接泄漏 | 代码里 `try` 没有 `finally close`，连接数只增不减 |
| 突发流量 | QPS 突然翻倍，连接池被打满 |
| 长事务 | `information_schema.innodb_trx` 里有跑了很久的事务 |

## 处置动作

- 紧急：临时调大连接池 + 加 `connectionTimeout` 熔断
- 找到慢 SQL：加索引或改写
- 连接泄漏：重启服务止血，同时修代码
- 长事务：`kill` 掉事务线程

## 注意

调大连接池只是止血，不是修复。数据库连接总数有上限，盲目调大会把数据库打挂。
